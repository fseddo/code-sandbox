Design a rate limiter

Cap request rate per client — where to put it, which algorithm, and how it survives going distributed.

scalabilitybackend

Step 1 · Understand the problem & scope

Clarify before designing — the interviewer is testing whether you nail down requirements:

  • Client-side or server-side rate limiting? (Server-side — client-side is trivially bypassed.)
  • Per-user, per-IP, or per-API-key?
  • What's the response when throttled? (HTTP 429 + Retry-After.)
  • Accuracy vs. throughput — is an approximate limit acceptable for lower latency?
  • Scale: how many requests/sec, how many distinct clients?

Step 2 · Back-of-the-envelope estimation

5M daily users · ~10 req/s at peak → ~50M req/s to evaluate. Each counter key ≈ 16 bytes; 5M active keys ⇒ ~80 MB — fits comfortably in a single Redis node, so a centralized store is viable before sharding.

Step 3 · High-level design

First decision: where the limiter lives. Middleware in front of the API servers is the usual answer.

PlacementProsCons
Client-side
  • No server cost
  • Trivially bypassed
  • Not enforceable
Server-side
  • Authoritative
  • Adds latency to every call
Middleware / gateway
  • Reusable across services
  • Centralized policy
  • Extra network hop
  • Must sync state across nodes

Step 4 · Design deep dive

Which counting algorithm? Each trades memory, accuracy, and burst behavior differently.

AlgorithmProsCons
Token bucket
  • Allows bursts
  • Simple, widely used
  • Two params to tune
Leaking bucket
  • Smooth, steady output
  • No bursts
  • Stale requests under load
Fixed window
  • Cheap memory
  • Easy to reason about
  • Edge-of-window spikes (up to 2×)
Sliding window log
  • Exact
  • Memory-heavy (stores every timestamp)
Sliding window counter
  • Accurate and cheap
  • Approximation at window boundary

Going distributed

Counter in Redis
INCR per key with TTL = window. One round-trip per request.
Race condition
Concurrent INCRs can read-then-write stale counts and overshoot the limit. Fix with an atomic Lua script or a sorted-set window.
-- atomic check-and-increment, evaluated server-side in Redis
local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return n <= tonumber(ARGV[2])
Multi-node sync
Centralize counters in Redis so every API node sees the same state; nodes stay stateless. Watch the added latency & the Redis single-point-of-failure (replicate it).

Wrap up

Recap the trade-offs you made (token bucket on a shared Redis, 429 + Retry-After). Where you'd extend with more time: per-endpoint policies, soft vs. hard limits, and monitoring the 429 rate to catch misconfigured clients.
